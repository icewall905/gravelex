# GravelEx + Pebble Health: serious fitness roadmap

Audit date: 2026-10-22. Scope: GravelEx Android fork, Pebble Time 2/watch apps, portable `health-hub`, HA, and contextual LLM output. This is a living engineering backlog, not a claim that the present system matches Garmin. Checkboxes mean implementation and review complete in source; the delivery ledger separately records deployment and field validation.

## Target outcome

A dependable, local-first daily training companion on GrapheneOS without Google services: reliable collection; useful workout load and recovery trends; explainable HRV and stress; a fast watch/phone/web overview; optional chest-strap/GPS inputs; portable deployment and recoverable history. Priorities remain training load, HRV and stress. Never turn absence of evidence into rest, inactivity or a reassuring score.

Garmin's load is an EPOC estimate, not the current zone-minute sum. Its readiness combines more inputs than our provisional weighted score. Build transparent alternatives with their own names/units instead of calling them equivalent. Reference: [Garmin training load](https://www.garmin.com/en-US/garmin-technology/cycling-science/physiological-measurements/training-load/), [Garmin training readiness](https://www.garmin.com/en-AU/garmin-technology/running-science/physiological-measurements/training-readiness/).

## Current phone-side capability boundary

This audit separates code-path support from proposed work. The fork's Room health path currently stores and queries minute steps/movement, sparse minute HR, watch-computed distance and calorie fields, sleep and walk/run/open-workout overlays, and firmware-dependent SpO₂ percent/quality. The phone can calculate summaries from those records, but it has no raw accelerometer, continuous beat intervals/PPI, respiration, route, power or cadence feed in this path. Minute BPM must not be turned into HRV. `HealthDataProcessor`, `HealthDao`, `Health.kt` and `docs/GRAVELEX_CAPABILITIES.md` are the source evidence; the capability audit does not prove that a watch or firmware has populated a field.

`PlatformHealthSync` writes steps, HR, sleep and exercise to the optional Health Connect API when permission and an available provider exist. `PebbleFitOxygenExportService` is a separate direct HTTPS exporter with encrypted token storage, paged cursors, retry/backoff and reconciliation; it exports health/session payloads and does not prove that a server is configured or that sensor coverage is real. Health Connect remains optional and cannot be the only storage or analysis path on GrapheneOS without Google services.

The existing Android geolocation bridge is for watchapp JavaScript, not a fitness recorder. `AndroidSystemGeolocation` chooses enabled FUSED (API 31+), then network, then GPS; `getCurrentPosition` returns the freshest last-known location when a provider is unavailable or a current request times out. That stale fallback and the lack of an accuracy/route policy must be audited before reusing it for exercise recording. The merged manifest currently declares location permissions in `libpebble3`, while the app's foreground services are typed for connected devices; no phone GPS recording service or GPX writer is implemented here.

## Execution order and definition of done

Work in the numbered order within each phase unless a reproducible data-loss defect takes priority. A task requires regression tests where behavior is material, independent review, a delivery record, and honest limitations. Firmware/hardware validation tasks can be blocked on real-world evidence; they must not be replaced with invented calibration constants. Avoid concurrent ownership of the same files.

Before expanding the recorder, complete these cross-cutting setup tasks in order:

- [ ] **S01 — Local-first storage and analysis parity.** Define one shared canonical observation/session model and method identity used by GravelEx local calculations, hub ingestion and optional Health Connect/HA adapters. Run analytics that need no backend directly in GravelEx (daily totals, recorded-session summaries, gaps, trend windows and quality/freshness labels); treat hub/HA as optional views and sync targets. Use shared fixtures for timestamps, DST, NULL versus measured zero, duplicate/replay, source precedence and stale data so local and server results are byte/comparison-equivalent where the method is the same.
- [ ] **S02 — Household ownership and portable export.** Attach every observation, workout and route to an explicit person/device owner; define migration for existing single-owner rows. Make per-person export, delete and retention controls optional but testable, and keep scoped upload tokens from crossing household owners. Acceptance includes an export/import fixture that preserves source, measured time, received time, method and unknown values without inventing records.
- [ ] **S03 — Supported metric inventory.** Publish a machine-readable inventory separating currently supported records (minute steps/movement, sparse minute HR, distance/calorie fields, sleep/activity overlays and firmware-dependent SpO₂) from exploratory watch sensors. Add a metric only when parser/API/storage evidence and a real sample path exist; do not promise HRV, PPI, respiration, continuous SpO₂, route, cadence or power from absent fields. Keep exploratory sensors out of readiness/load until source, unit, quality and coverage are demonstrated.
- [ ] **S04 — Audit provider selection and stale fallback.** Test `AndroidSystemGeolocation` provider ordering, disabled providers, last-known age, timeout behavior, clock changes and reconnects on GrapheneOS. Replace implicit stale success with an explicit age/accuracy/source status for route recording; preserve stale locations only for callers that opt into them. Add fixtures for provider loss, duplicate timestamps and out-of-order fixes before sharing the bridge with a recorder.
- [ ] **S05 — Phone-assisted GPS recorder design.** Specify watch start/pause/resume/finish commands and a phone-owned recording session before implementation. The design must cover explicit foreground location permission and a user-visible location foreground service, foreground/background lifecycle, accuracy and impossible-jump filters, battery budget, watch/phone reconnect, process death/reboot recovery, route privacy/retention, GPX export, and optional uploads to HA or the hub. No GPS implementation or route upload is claimed by this roadmap until the acceptance matrix is tested on GrapheneOS without Google services.

- [ ] **S06 — Useful and fun derived metrics audit.** Evaluate daily movement patterns, sleep consistency, workout streaks/records, watch battery trends and step-derived cadence only with clear source/coverage labels. Investigate light-intensity/orientation fields as raw device signals, not calibrated lux/daylight exposure or verified wear detection. For future GPS sessions, evaluate splits, personal-best segments and elevation gain with location/altitude quality gates. Maintain a per-watch/firmware capability matrix and keep unsupported hardware or diagnostic PPI out of physiological scores.

- [x] **F02 — Freshness gate for readiness load.** Accept confirmed training only through today or yesterday; reject future, stale and undated inputs independently of a `ready` label. ### GPS reference material (checked 2026-10-24)

[Android LocationManager](https://developer.android.com/reference/android/location/LocationManager) provides a platform GNSS provider; keep this path independent of Google Play services. [Android location foreground-service rules](https://developer.android.com/develop/background-work/services/fgs/service-types#location) govern screen-off workout recording. [PebbleKit JS](https://developer.repebble.com/docs/pebblekit-js/) exposes phone geolocation to watchapps. These APIs support the proposed design; they do not establish that a tested GravelEx running recorder exists.
